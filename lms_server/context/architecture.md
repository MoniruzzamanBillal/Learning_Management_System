# Architecture

## Stack

| Layer | Technology | Role |
| --- | --- | --- |
| **Runtime/Framework** | Node.js + Express 4 | HTTP server and routing. |
| **Language** | TypeScript | Static typing across routes/services/models. |
| **Database** | PostgreSQL via Prisma (pinned to Prisma 6, not the latest major — see below) | Persistence for all domain models. Migrated from MongoDB/Mongoose per [`context/specs/19-postgres-prisma-migration.md`](specs/19-postgres-prisma-migration.md); IDs are UUID strings (Postgres `id`, not Mongo `_id`). |
| **Auth** | `jsonwebtoken` | Access-token issuance/verification (`config.jwt_secret`). |
| **Validation** | Zod | Request-body schema validation via `validateRequest`. |
| **File/Video Upload** | Multer + `multer-storage-cloudinary` + Cloudinary | Course cover images and course videos. |
| **Payments** | `sslcommerz-lts` (SSLCOMMERZ) | Course payment processing. |
| **Email** | Nodemailer | Transactional email (`src/app/util/sendEmail.ts`). |
| **Other** | `pdf-lib` | Used for certificate/PDF generation. |

## System Boundaries

- `src/server.ts` — process entry point: connects the Prisma singleton (`prisma.$connect()`), then starts the HTTP listener. No longer touches Mongoose at all.
- `src/app/util/prisma.ts` — the Prisma Client singleton (`export default prisma`), using the standard serverless-safe pattern (attaches to `globalThis` outside production so dev hot-reload doesn't exhaust connections). Import this in services rather than instantiating `new PrismaClient()` directly.
- `prisma/schema.prisma` — the entire data model: 9 domain models plus the `CourseInstructor` join model (Course↔User many-to-many, replacing Mongo's denormalized `Course.instructors`/`Course.modules` arrays) and 3 enums (`UserRole`, `PaymentStatus`, `VideoStatus`). Pinned to **Prisma 6** (`prisma`/`@prisma/client` both `6.19.3`), not the latest major (7) — Prisma 7 replaced schema-level `url`/`directUrl` and the classic `@prisma/client` import with a driver-adapter model (`prisma.config.ts` + `@prisma/adapter-pg`); the pin keeps the setup this repo actually uses (and the migration spec) working as documented. IDs are `id String @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid` on every model, generated Postgres-side via `pgcrypto`.
- `src/app.ts` — Express app composition, in order: CORS (explicit origin allowlist) → `express.json()` → `morgan("dev")` → `cookieParser()` → `body-parser` urlencoded → `MainRouter` mounted at `/api` → root `GET /` health check → `globalErrorHandler` → catch-all 404 handler. This order matters — the error handler must come after routes and before the 404 handler.
- `src/app/router/index.ts` — aggregates every module's router and mounts it under a path prefix (`/user`, `/auth`, `/course`, `/module`, `/video`, `/enroll`, `/payment`, `/review`, `/ai`, `/error-log`), all under the `/api` base from `app.ts`.
- `src/app/modules/<name>/` — one directory per domain resource: `auth`, `user`, `course`, `courseModule`, `VideoModule`, `VideoProgress`, `CourseEnrollment`, `payment`, `SSL`, `review`, `ai`, `errorLog`. Not every module has every file below, but the split is consistent:
  - `*.route.ts` / `*.routes.ts` — Express router; wires middleware (`authCheck`, `validateRequest`, `upload`) to controller methods.
  - `*.controller.ts` — thin; wraps a service call with `catchAsync` and responds via `sendResponse`.
  - `*.service.ts` — business logic and Prisma queries (`import prisma from "../../util/prisma"`).
  - `*.model.ts` — no longer exists for any domain model; the schema lives entirely in `prisma/schema.prisma` now. (Mongoose model files were deleted module-by-module as each was rewritten; a few were kept temporarily as decoupled, DB-disconnected "legacy shim" types during the migration so not-yet-rewritten sibling modules still compiled — none remain.)
  - `*.interface.ts` — most now just re-export the generated Prisma type as the module's `T*` alias (e.g. `export type TUser = User;` from `@prisma/client`) to minimize call-site churn; a few (e.g. `course.service.ts`'s `TAddCoursePayload`) define a narrower local payload type where the Prisma model type doesn't match the actual request shape (e.g. a create payload that also carries a join-table `instructors: string[]`).
  - `*.validation.ts` — Zod schemas. Any ID field validator is `z.string().uuid(...)`, not the old `z.string().refine(mongoose.Types.ObjectId.isValid, ...)`.
  - `*.constants.ts` — enums/constants (e.g. `UserRole`, `PAYMENTSTATUS`) — unchanged, their strings match the Prisma enum values exactly.
  - `VideoProgress` and `SSL` have no `route.ts` — they're internal-only, consumed directly via `prisma.videoProgress.*` from `CourseEnrollment`, `VideoModule`, and `ai` services (and the `payment` module for `SSL`), not exposed as their own HTTP surface. `VideoProgress.service.ts`/`VideoProgress.controller.ts` are empty files (0 bytes) — all its logic lives in `videoProgress.functions.ts::addVideoCoursePublish`, called from `VideoModule/video.service.ts` inside a `prisma.$transaction`.
  - `ai` has no `ai.validation.ts` for its GET endpoint — it's stateless per-request (no dedicated table), and its first endpoint (`GET /ai/review-summary/:courseId`) takes no body to validate. It calls `askOpenRouter` (`src/app/util/openRouterClient.ts`) and caches results directly on the `Course` row (`aiReviewSummary`, `aiReviewSummaryReviewCount` columns) rather than its own table.
  - `errorLog` has no `errorLog.validation.ts` for its GET routes (no request body). `errorLog.route.ts` exposes `GET /` and `GET /:id` (`authCheck(UserRole.admin)`) plus `GET /cleanup` (see below) — rows are otherwise written exclusively from inside `globalErrorHandler`, never via a public write endpoint. **Mongo's TTL index has no Postgres/Prisma equivalent** — 30-day retention is now enforced by a Vercel Cron job hitting `GET /api/error-log/cleanup` daily (`vercel.json`'s `crons` entry, `"0 3 * * *"`), gated by `src/app/middleware/verifyCronSecret.ts` checking the `Authorization: Bearer <CRON_SECRET>` header Vercel's cron invocation sends automatically (`config.cron_secret`) — not `authCheck`, since this isn't a user-JWT flow. Registered before `GET /:id` in the route file so it isn't swallowed by that param route.
  - `review` supports soft-delete moderation: the `Review` model has `isDeleted`, filtered explicitly with `isDeleted: false` at every relevant Prisma call site (no automatic query-hook equivalent to Mongoose's `pre("find")` exists) — `getAverageReviewOfCourse`'s `prisma.review.aggregate(...)` needs the same explicit filter aggregations always did. `GET /review/all` and `DELETE /review/:reviewId` are both `authCheck(UserRole.admin)`; deleting a review resets the underlying enrollment's `isReviewed` flag so the student can leave a new one. `Review` also now has a DB-level `@@unique([userId, courseId])` (new in Postgres, not present in Mongo) — `addReview` catches the resulting `Prisma.PrismaClientKnownRequestError` (`code: "P2002"`) and rethrows a friendly `AppError` rather than letting the raw Prisma error surface.
- `src/app/middleware/` — cross-cutting middleware (see below).
- `src/app/util/` — shared helpers: `catchAsync.ts`, `sendResponse.ts`, `SendImageCloudinary.ts` (Multer/Cloudinary storage config for images), `VideoUpload.ts` (video-specific upload config), `sendEmail.ts`, `prisma.ts` (Prisma Client singleton, see above).
- `src/app/Error/` — `AppError` class plus normalizers for Zod/Mongoose validation/cast/duplicate-key errors, consumed by `globalErrorHandler`. **Known gap, not yet addressed:** `handleCastError.ts`/`handleValidationError.ts` and the corresponding branches in `globalErrorHandler.ts` (`error.name === "ValidationError"`/`"CastError"`, `error.code === 11000`) are dead code post-migration — no Mongoose operation can throw them anymore — but were left in place as out-of-scope for the Postgres migration itself; `mongoose` remains a `package.json` dependency solely so these files' `mongoose.Error.*` type imports still compile. Prisma's own error types (e.g. `PrismaClientKnownRequestError`) are *not* normalized by `globalErrorHandler` generically — only handled per-call-site where a friendly message matters (see `review` above).
- `src/app/config/index.ts` — the single place `process.env` is read (Postgres `DATABASE_URL`, JWT secret, Cloudinary, Nodemailer, SSLCOMMERZ store credentials/URLs, `CRON_SECRET`). New code should import `config` rather than reading `process.env` directly. **`DATABASE_URL` is the same env var name Mongoose used** — its value was repurposed in place from a Mongo URI to a Postgres connection string, not renamed.

## Middleware

- `authCheck(...requiredRoles: TUserRole[])` — verifies the `Authorization: Bearer <token>` JWT, attaches the decoded payload to `req.user`. Called with no roles to just require *some* valid token, or specific `UserRole` values to restrict access.
- `ValidateCourseAccess` — used on `CourseEnrollment` routes that serve paid content; requires both a matching `CourseEnrollment` row and a `Payment` row with `paymentStatus === Completed` for that user+course (`prisma.courseEnrollment.findFirst`/`prisma.payment.findFirst` — `findFirst`, not `findUnique`, since both combine multiple non-unique filter fields), else throws `403`.
- `verifyCronSecret` — checks `Authorization: Bearer <CRON_SECRET>` against `config.cron_secret`; gates `GET /error-log/cleanup` (Vercel Cron only, not a user-JWT flow).
- `validateRequest(zodSchema)` — parses/validates `req.body` against a Zod schema, throwing `ZodError` on failure (normalized by `globalErrorHandler`).
- `globalErrorHandler` — normalizes `ZodError`, Mongoose `ValidationError`/`CastError`, MongoDB duplicate-key (`code: 11000`), and `AppError` into one JSON error shape (`{ success: false, message, errorSources, stack }`), and persists every error (all 4xx/5xx, not just unexpected bugs) via `errorLogServices.logError(...)` before responding — see [`context/specs/09-observability-logging-and-error-tracking.md`](specs/09-observability-logging-and-error-tracking.md).
- `rateLimiter.ts` — `aiLimiter` (10 req / 10 min per IP, applied to `POST /ai/course-advisor` and `GET /ai/review-summary/:courseId`) and `loginLimiter` (10 req / 15 min per IP, applied to `POST /auth/login`), both built on `express-rate-limit`. Runs first in each route's middleware chain so no DB/LLM work happens before the count. In-memory store — would need Redis if the backend scales past one instance. See [`context/specs/06-rate-limiting.md`](specs/06-rate-limiting.md).

## Auth & Access Model

- Users authenticate via `POST /api/auth/login`, receiving a JWT signed with `config.jwt_secret` and containing at least `userId` and `userRole`.
- Every protected route calls `authCheck(...)` with the roles allowed to hit it.
- Course-content routes additionally require `ValidateCourseAccess` (enrollment + completed payment), independent of role.
- **Resolved gap:** `course.controller.adminStatistics` (`/course/admin-stats`), `moduleController.addModule` (`/module/add-module`), and `videoController.addVideo` (`/video/add-video`) previously had `authCheck(...)` commented out; re-enabled per [`context/specs/05-security-authcheck-and-hardening.md`](specs/05-security-authcheck-and-hardening.md) — `/course/admin-stats` requires `UserRole.admin`, the other two require `UserRole.admin`/`UserRole.instructor`, matching sibling routes in the same files.

## Invariants

1. **Response envelope:** every controller responds via `sendResponse<T>(res, { statusCode, success, message, data, token? })` — don't hand-roll `res.json(...)` in new controllers.
2. **Async error propagation:** every controller/middleware handler that can throw is wrapped in `catchAsync` so errors reach `next(error)` and the global handler, rather than crashing the process or being swallowed.
3. **Validation before controller:** any route accepting a body goes through `validateRequest(schema)` before the controller runs.
4. **Multipart + JSON pattern:** routes that accept a file *and* structured JSON fields (e.g. `add-course`, `update-course`, `add-video`, `update-video`, `update-user`, `register`, `register-instructor`) run `upload.single(...)`/`uploadVideo.single(...)` first, then an inline middleware that does `req.body = JSON.parse(req.body?.data)`, then `validateRequest`. New file-upload endpoints should follow this exact order.
5. **Config centralization:** all environment variables are read once in `src/app/config/index.ts` and imported from there.
6. **Module self-containment:** a new domain resource gets its own `src/app/modules/<name>/` directory following the file split above, registered in `src/app/router/index.ts` — don't bolt unrelated logic onto an existing module.
7. **Explicit soft-delete filtering:** there is no Prisma equivalent of Mongoose's `pre("find")`/`pre("findOne")` query hooks. `User`, `Module`, `Video`, and `Review` are the four models that had that hook in Mongo — every Prisma query against them must add `isDeleted: false` to `where` explicitly, at the call site (`CourseEnrollment` and `Payment` also carry `isDeleted` but were never auto-filtered even in Mongo, so don't add the filter to them by default — only where a call site already filtered manually). New queries against these four models must not forget this filter.
8. **`findFirst`, not `findUnique`, when combining a unique field with other conditions:** Prisma's `findUnique` can only take the unique field(s) in `where` — it cannot also carry e.g. `isDeleted: false` in the same call. Any lookup that needs both (which is most soft-delete-filtered lookups by `id`) must use `findFirst` instead, even though `id` is unique. Plain "does this ID exist at all" lookups with no extra condition can still use `findUnique`.
9. **Video ordering — partial unique index lives outside `schema.prisma`:** Prisma's schema DSL can't express a partial (`WHERE` clause) unique index, so `Video`'s real uniqueness guarantee — `UNIQUE ("moduleId","videoOrder") WHERE "isDeleted" = false` — is a hand-added `CREATE UNIQUE INDEX` statement inside the generated init migration's `migration.sql`, not anything visible in the schema file itself (which only has a plain `@@index` for query performance). This survives future `prisma migrate dev` runs (applied migrations are immutable) but **must be manually re-added** if this migration is ever reset/replayed via `prisma migrate reset`.
